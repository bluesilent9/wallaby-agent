# Build 66 — locally paired encrypted peers

Wallet Server is an untrusted courier. Build 66 adds persistent Agent/Mobile permission grants, Noise-encrypted peer channels, credential-free v3 wallet transfers through the existing Server SSH connection, independent producer agreement for v2 multisig creation/refresh, and signed public review QR records. The Server cannot grant a pairing, decrypt a private file, manufacture a peer approval or silently downgrade a new operation to IP-based trust. It can withhold traffic and metadata remains visible. Existing public coordinator/RPC traffic is not claimed to be end-to-end encrypted.

## Connect devices

Install matching Wallet Server V1 Build 2 before advertising these new capabilities. Close protected work normally before upgrading the Agent. Existing profiles, Core wallets, signing keys, archive contents, identities and denial/retirement records are retained; Bitcoin keys are never regenerated by pairing. OPAQUE enrollment and multi-device password login belong to Server/Mobile account access. This Agent retains its established SSH/application-token connection and does not ask for that account password.

Open **Peer Connections** in the protected window. On an Agent, choose **Pair another Agent** or **Pair a Mobile**. Obtain the signed, two-minute QR directly from this screen. A Mobile scans it; another Agent can import its complete signed QR text through an independently trusted local transfer. Do not obtain the pairing secret solely from Server. The issuing Agent then shows the candidate's full identity, requested permission and channel code for local acceptance. Compare the code on both devices. A role is a locally granted permission, not proof of what operating system runs a key. Grant Agent authority only to a trusted Agent computer; a phone gets Mobile authority.

The invitation is single-use. Changing a pinned identity, Noise key or role requires explicit local revocation and a fresh QR. Saved peers reconnect with fresh Noise ephemeral keys and channel IDs. Revoking immediately closes local channels and pending streams; it cannot recall ciphertext already handed to the relay or undo a completed remote action. Approval is not persisted until the other endpoint proves possession of the handshake keys. Unapproved/expired candidates cannot perform application actions.

The protected worker still has a read-only persistent filesystem. A separate unprivileged, same-UID, AF_UNIX-only service writes a fixed 0700 directory and 0600 file under `/var/lib/wallaby-agent-peers/<uid>`. Its exact bounded schema accepts only the communication private key, pair-specific PSKs, public identities/roles and consumed invitation IDs. It accepts neither file paths, commands, Bitcoin private keys nor arbitrary wallet records. The service disables swap/core dumps and cannot read home directories. Existing denial storage remains a separate schema and service. Pairing grants are device-local, not Server-profile data.

## Cryptographic and application contract

Use the Server Build 2 `SECURE_RELAY.md` invitation/prologue/frame/control schemas unchanged, with **Noise_IKpsk2_25519_ChaChaPoly_SHA256**. The pinned MIT `noiseprotocol 0.3.1` implementation is shipped as source under `src/noise`; it uses the installed `python3-cryptography` primitives. See `NOISE_LICENSE` and [Noise's specification](https://noiseprotocol.org/noise.html). The full invitation is SSHSIG-signed in `wallaby-wallet-peer-invitation-v1`. Both handshake payloads are envelopes in `wallaby-wallet-peer-handshake-v1` over exactly:

```
{protocol:"wallaby-wallet-relay",version:1,kind:"handshake",
 prologue_hash:SHA256(canonical_prologue),initiator:PROLOGUE_INITIATOR,responder:PROLOGUE_RESPONDER}
```

The responder verifies the decrypted Noise static key against that identity. The initiator pins the responder static key from the independent QR. The signed role-bound participants, invitation PSK and prologue must all match. No application authority exists before both the handshake and local grant complete. Each endpoint sends an encrypted `grant` with operation hash equal to the prologue digest and body `{accepted:true}`. An initial responder sends it only after its human accepts; a previously paired endpoint may grant reconnection from its local record. Both sides require the other's authenticated grant before becoming ready.

Encrypted plaintext records have exactly:

```
{protocol:"wallaby-wallet-relay",version:1,header:OUTER_HEADER_WITHOUT_CIPHERTEXT,
 role:AUTHENTICATED_SENDER_ROLE,operation_hash:64_HEX,payload_type:TYPE,
 expires_at:UTC_INTEGER,body:TYPE_BODY}
```

Compare every repeated outer field, channel, direction, role and operation. Counters are contiguous independently in each direction. A duplicate identical frame ID is idempotent; a changed ID/header, altered ciphertext, repeated counter or changed transcript closes/refuses that channel. New ephemeral keys are used on reconnection. Signed Server control reports remain advisory; local peer state enforces readiness independently.

Application types: `grant`; `ping`/`pong`; `policy_agreement` with `{scope:"proposal"|"policy"|"refresh",digest:CANONICAL_CONTENT_HASH}`; `verification_request`/`verification_record`; and the Agent-only stream records below. Normal grant/policy records last 120 seconds. Streaming and liveness records may last at most 3,600 seconds so a retained Server receipt queue can drain without re-encrypting a queued frame. Policy approvals additionally require recent matching agreement on the current authenticated channel; a stale/paused channel cannot authorise new work.

## Wallet creation and refresh

New multisig setup proposals use v2 and the exact required distinct Agent identities. Several node/disc signer roles on one Agent need one pairing to that Agent, not one pairing per key. Opening review exchanges the exact proposal digest over those channels. Before key generation, including after password entry, require matching peer agreement. Complete-policy approval similarly requires agreement on the exact signed contributions, public proposal and derived receive/change policies. Local Core/network checks and address, threshold, block-height/time and physical-backup reviews remain.

Refresh v2 uses the same peer requirement object. Its shared agreement hashes the exact previous descriptors, new receive/change descriptors and history timestamp, not per-node wallet labels/request IDs. Every local signer is still discovered and verified locally. Missing/disagreeing channels block before unlocking/importing, and agreement is repeated after passphrase entry. Reopening a cached funding review refreshes only peer liveness/agreement; it does not repeat the long blockchain scan. Ordinary amount/address/height review remains local, and replacement-disc verification/destruction is unchanged.

Previously delivered immutable v1/v2 requests may be reconciled without rewriting signed hashes. The exchange refuses a newly introduced legacy multisig or sync invitation. Old pre-upgrade work that was never delivered may need explicit cancellation/reconciliation in Server rather than being silently converted or replayed. Single-signature requests that need no producer mesh keep their existing path.

## Encrypted synchronisation

New transfer/preview v3 binds both endpoints, Ed25519 identities and Noise keys. IPv6 fields are null; new requests never use peer IPs, SSH listener setup or another computer's login password. The sender preview must be signed by the already QR-pinned sender and repeat the complete transport/restoration purpose. Both users still select exact wallets and authorise locally. The existing authenticated SSH tunnel to Server is retained.

The stream begins with an Agent-only `stream_open` body `{stream_id,transfer_id}`. Its operation hash is SHA256 of the full transfer proposal omitting only `direction`, `peer` and `node_ipv6`; all common immutable fields remain. The receiver must have an exact pending, locally authorised selected request and a matching pinned channel before opening its internal socket. `stream_ready` has `{stream_id}`. `stream_data` has `{stream_id,offset,data:BASE64,sha256}`, at most 16,384 decoded bytes, contiguous per-direction byte offsets and a digest. `stream_ack` has `{stream_id,offset}` and is sent only after bounded processing/consumption. `stream_close` has `{stream_id}`. At most four streams and four incoming chunks per stream are admitted. Every record also carries the authenticated outer header and operation hash above.

Inside that encrypted stream, the tested Core/file protocol is retained: Core-validated block catch-up while receiver Internet peers are paused, complete size/hash verification before restore, encrypted/locked private backups, independent policy/history verification, native Extinct history/LOST labels and exact original private-role restoration. A Mobile cannot enter this path. Original-role restoration still rejects another private cosigner sharing the same public policy, and extinction/restoration requires no missing signer or Bitcoin signing quorum.

Ambiguous delivery retries the identical queued ciphertext/frame ID, not a wallet action. Server backpressure retains that frame and acknowledged stream offsets with bounded RAM; it does not regenerate keys or create repeated wallet jobs. **A Server/peer restart that loses the stream is not advertised as an automatic wallet-resume feature:** re-handshake is automatic for the saved pairing, but an attempted private transfer remains recovery-required until locally reconciled. Partial receive files are removed; no partial file reaches Core and completed/uncertain operations are not replayed. A later resumable-file protocol would require explicit staged-file/digest reconciliation on both clients.

Server Build 2's 120 new frames/minute/sender and 1,024 live messages plus 30-minute receipt retention impose a significant bulk-transfer limit, especially with encrypted application ACKs. Full queues pause safely (up to a bounded 40-minute stream wait), but multi-gigabyte catch-up may be very slow. The Server needs a streaming/bounded-receipt improvement for practical bulk throughput; the Agent cannot bypass its queue policy. This limitation is reported on Synchronisation and in the Server handoff.

## Mobile verification

A paired Mobile has public verification reads only. `verification_request` has body `{request_digest:operation_hash}` and returns a signed `verification_record`. Operation review QR/envelopes use namespace `wallaby-wallet-verification-v1` and exactly:

```
{protocol:"wallaby-wallet-verification",version:1,kind:"operation_review",
 request_digest,proposal_digest,operation_kind,agent_public_key,agent_fingerprint,
 local_route:{ssh_host_public_key,ssh_host_fingerprint,ipv6,hostname},
 legacy_peer:LEGACY_PROPOSAL_PEER_OR_NULL,peer_transport:PINNED_TRANSPORT_OR_REQUIREMENTS_OR_NULL,
 generated_at,expires_at,approval_authority:false}
```

Local route fields come from the Agent, with null where no local SSH host key/routable IPv6 exists. A legacy peer route is explicitly a claim requiring the peer's own independent scan. Expiry is 120 seconds. Completed/withdrawn requests are refused. No raw PSBT, wallet file, passphrase or peer PSK is returned. Mobile/Server comparison success never triggers signing, building, deletion or broadcast. Keep reviewing actual wallet addresses, amounts and unlock times on the Agent.

Server 2's older `wallet_mobile_verification_v1` facts validator requires a routable local IPv6 and actual local SSH Ed25519 host key. Advertise that optional legacy facts capability only when those facts exist; new Noise pairing itself requires neither inbound SSH nor discoverable Agent addresses. The Android application is a separate build and still needs this matching client implementation/interoperability testing.

## Validation and limits

Tests use invented keys/passwords and isolated Core 31 regtest nodes. They exercise the actual companion Server dispatcher and a real Core wallet transfer through it, real two-Agent vault creation, private and watch-only relay restoration, old/current/static/HD signer compatibility, wrong PSK, transcript/header/role/key substitutions, revoked/unapproved/expired peers, replay/order failures, independent mesh agreement, downgrade refusal, backpressure, retained ciphertext and durable storage schema/symlink checks. Browser checks cover protected navigation, QR display and revocation; existing disc, transaction, cancellation and extinction UI/regression checks remain. No real wallet, installed service, SSH account or physical disc was changed. The new installed systemd/Qt helper and a future actual Mobile client still need deployment testing; source/DEB parity is audited separately.
