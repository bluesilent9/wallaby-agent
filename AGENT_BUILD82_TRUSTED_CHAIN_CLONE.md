Keep both Agents on Build 82 and connected through their independently paired direct SSH connection. On a local Wi-Fi network the direct connection carries the bulk data; Wallet Server continues to provide signalling only.

The receiver pauses its Internet peers, stages the complete cold snapshot, verifies every file and the inventory, and only then stops its own Core to install it. The modern complete-history transfer imports public Core transaction records, confirmed block associations, fixed addresses and labels, including LOST information. It does not require replaying old blocks that have already been pruned. The genuine-pruning test exercises cloning first, then importing previously absent complete Extinct history without a history-recovery job or Internet blockchain download.

If Treasury (2022–2026) is still an active wallet on Treasury Australia, that laptop must approve its own retirement first. First-time history import is allowed for previously unknown historical addresses, but local active ownership, an unfinished retirement or a recorded restoration blocks duplication. ## Three separate sections

- **Wallets** retains the alphabetic unified table, signer details, watch-only controls and persistent receive denials.
- **Blockchain** separates validated catch-up from trusted cold cloning, groups source permissions under a disclosure, shows the selected source and clone progress, and clearly reports paused Internet peers. The selected source survives polling and page redraws.
- **Local history** retains the separately approved rescan/recovery controls. Wallet transfer and recovery controls are unavailable while cloning is active. The active section survives polling.

## Catch-up and clone eligibility

Ordinary catch-up still asks Core to validate each block. A pruned source works only if it retains the range after the common ancestor. A behind or still-downloading source can serve a validated prefix and later deliver more. A receiver ahead of it keeps its chain and waits. No lack of source blocks marks the receiver's blocks invalid. Catch-up does not provide arbitrary backfill of pruned old blocks.

Cloning explicitly trusts the source's existing validated chainstate; it is not independent validation from genesis. It requires the same Bitcoin Core 31 release, the same network, the receiver's current tip as an ancestor of the source, a source at least as high as the receiver, and enough retained blocks for the receiver's existing wallet history. It refuses pruning gaps, a pruned source for a receiver configured as a full archival node, optional receiver indexes, AssumeUTXO snapshot layouts, unsupported/custom blockchain paths, unexpected files, links, insufficient staging disk space and unresolved earlier clone stages. Neither bitcoin.conf nor the receiver's pruning budget is changed. Full → full, full → pruned and eligible pruned → pruned are supported. Pruned → full requires a full source or a separate local configuration change; the clone does not silently change that choice.

A source may itself still be downloading. Cloning pauses that source while its consistent snapshot is sent, then restores its previous Internet activity. Receiving Internet peers remain paused until the user explicitly resumes them. The existing block catch-up controls can continue direct downloading after a clone. Client/server direction of the direct SSH connection does not determine which Agent can serve.

## Filesystem and interruption boundaries

A dedicated unprivileged helper accepts only the protected worker's UID and system-service cgroup. Its protocol never accepts a remote command or arbitrary destination path. Supported roots are the desktop user's normal native/Snap Core network data directories. Only `blocks/` (including the block index and XOR key) and `chainstate/` cross the clone stream. No wallet database, cookie, settings, configuration, optional indexes, pairing trust or signing authority is copied. File paths use a closed grammar and component-wise no-follow opens, regular-file/owner/link checks, bounded 1 MiB reads, file checksums and a final inventory checksum. Disk staging requires free space for the incoming snapshot plus a safety reserve while retaining the receiver's existing chain.

The helper preflights the actual local Core launcher in the independent desktop user service manager before stopping Core, waits for its process and exclusive data lock to be released, and restarts it without a terminal. A transfer disconnect restarts the source and discards an uncommitted receiver stage. Installation records its phase and retains the old directories until Core reopens the reviewed tip and original loaded wallets retain their descriptors and at least their earlier transaction counts. A failed directory swap rolls back. An unresolved crash stage requires local reconciliation rather than a blind replay or deletion. Abrupt power loss or killing the helper can require manual Core/reconciliation work; the implementation cannot guarantee an automatic restart after arbitrary process destruction.

Only a live locally authorised clone thread and its bounded progress/restart deadline extend the protected workspace's Core restart grace. Saved flags, Wallet Server messages and a stale state file cannot do so. Automatic cookie discovery retains the already-bound cookie location during that planned shutdown. Mutating wallet, recovery and network controls are blocked while cloning. Source clone permission is consumed once and expires when the protected workspace closes. Mobile peers cannot open clone streams.

## First-time and named Extinct archives

`Wallaby Extinct`, `Extinct` and `extinct_watch` are recognised public fixed-address archive aliases. One existing local alias is updated in place; multiple ambiguous containers require local reconciliation. A name never supplies private-key or history authority. Complete coverage must come from the approved authenticated direct history packet and be anchored to the receiver's own active chain. A bare Server offer, summary, address list or invalid coverage cannot authorise first-time history import. Legacy/v1 history retains its previous local-extinction requirement. No new Wallet Server protocol or bulk relay is introduced.

## Validation and limits

The Build 82 tests run isolated Bitcoin Core 31 regtest instances and actual paired direct SSH sessions. They cover cold-clone reopen, receiver private-wallet/history retention, genuinely deleted pruned blocks followed by first-time complete Extinct history import and LOST label preservation, source restart after direct-stream interruption, full/pruned eligibility, source-behind refusal, unsafe paths/links, corrupt streams, insufficient space and atomic-swap rollback. Native public history regression tests retain receiver-only history, validate signed packet scope and active-chain coverage, and refuse conflicting LOST labels, local active owners and uncovered receiver-only legacy entries. Existing extinction continuation/deletion evidence and Core restart tests remain applicable.

Tests replace the desktop user systemd launcher with isolated child Core processes because CI does not provide the user's desktop service manager. Service construction/preflight is covered separately. This is not an on-device test of the user's Snap installation, Wi-Fi throughput, storage capacity or power-failure behavior. No production wallet, node, service or physical disc was modified during development.
