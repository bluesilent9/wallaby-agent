# Build 103 — Reconcile existing verified Extinct history

The supplied logs show a complete direct transfer: 38 addresses and 51 native transaction records exported and the same counts certified on the receiver. The remaining preservation request was not evidence that this history had been erased. The Agent's existing-preservation shortcut required the old active wallet to be present for comparison. When that original was gone, the request could remain as a new preservation approval despite a verified archive already containing every requested record.

Build 103 compares the exact validated preservation manifest against the real local Core archive: descriptor-derived address membership, labels including LOST text, confirmed stored transaction bytes/IDs and active-chain block references, plus current whole-archive coverage. When no local original remains, existing valid archive coverage permits a read-only preservation receipt. When an original exists, including unloaded copies, its local records are still compared and its prior loaded state is restored. Counts alone do not establish preservation. Conflicts, missing records and unverified archives remain unresolved and cannot fabricate completion.

An idle, bounded reconciliation pass checks at most one eligible preservation indication, throttles retries, respects denials/cancellation and active transfer/history work, and reports only already-existing verified records. It never invokes approval, imports, rescan, download, wallet replacement or deletion. Repeated Server delivery of the same completed indication cannot restart a wallet operation. The Server protocol and signed receipt schema are unchanged; the existing Server verifies the receipt/readback and stops that request. No Server update is required for this fix.

Read-only verification reports carry an internal completed-record basis, separate from mutating preservation operations. Only an exact matching read-only result can cease to block safe closure while awaiting Server delivery; actual mutations, signing results and uncertain outcomes retain their barriers. An authorised recovery continuation also recognises an already-reconciled result and does not approve/import it again. Any original-wallet deletion always remains a separate local approval.

Diagnostics record comparison counts and fixed match/coverage/original-presence flags, and distinguish missing address, label conflict, missing transaction and chain mismatch without exporting addresses, labels, transactions or keys. Tests reproduce direct receiving between pruned Core nodes followed by a late preservation indication with no original wallet, verify automatic satisfaction with no import/deletion, check matching unloaded originals, missing/conflicting/unverified history, idempotence, continuation handling, safe closure, and the existing direct sync/denial/policy flows. Physical user nodes were not used in tests.
