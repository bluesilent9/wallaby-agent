# Build 100 — Advisory cancellation notices cannot trap the workspace

Build 98/99 can refuse safe closure with no pending requests or Core work when a retirement cancellation remains queued for the Server. This is a non-mutating advisory outcome. It can be re-established from current node facts after reconnecting and is not authority for wallet deletion.

Build 100 permits safe closure for retirement cancellation/denial results without recorded wallet deletion or archive verification. Actual active Core operations, prepared history recovery, uncertain/error results, completed imports/preservation/deletion and transaction signing results remain barriers. Advisory notices remain queued during the session; normal safe closure can clear them with RAM. No completion is fabricated or mutation undone. Refused-close logs now include fixed delivery-kind/status categories and counts, never payloads, keys or transaction contents.

The guarded recovery helper in packaging/close_notice_recovery.py supports an existing Build 98/99 service. It verifies published runtime hashes, enters the existing protected namespace/cgroup, enforces RAM, filesystem, swap, dump and inhibitor checks, refuses all active wallet/archive/history work, and removes only one schema-limited retirement cancellation/denial notice. It then requests normal safe closure from outside that inspector. It never force-stops the service or changes wallets. A different result requires its own inspection.

Validation checks safe-close behaviour using both actual busy classification and notice classification; critical/uncertain results and in-flight Core reservations remain protected. Recovery tests verify that completed, signing and mutating outcomes cannot be discarded, loaded archives/history jobs cause refusal, and durable decisions/completed records remain intact. Current release identity and direct-SSH discovery/receiving regressions are also checked. Build 99's native Extinct merge and paired Agent trust boundaries are unchanged. The privileged recovery's Linux namespace execution still requires confirmation on the affected laptop; it is guarded to refuse failed protection checks.
