# Build 19 diagnostic logs

Services now ends with **Logs → Save terminal activity log**. Like Dashboard, it exports UTF-8 text through the authenticated local page as `Wallaby_Agent.log`, retains seven UTC days, and limits each day to 1 MiB. Older entries are discarded when the cap is reached. Times are UTC; every line identifies `protected` or `unprotected` and a source/action category.

Ordinary service transitions are recorded under `~/.config/wallaby-agent/diagnostics` (or the configured XDG configuration root). Protected action outcomes, node connection transitions and cancellation receipt events are recorded only under the protected non-swapping RAM mount. Log files/directories are owner-only; cross-process file locking, bounded reads, atomic replacement and symlink/hardlink checks protect consolidated storage.

Only fixed action names, safe categories and controlled diagnostic messages are recorded. RPC arguments/results, wallet files, proposals, passphrases and raw exception text are never log inputs. Defence-in-depth redaction replaces extended keys, WIF/private key data, Bitcoin addresses, descriptors, PSBTs and opaque key/transaction data with typed `[REDACTED: …]` placeholders before storage and again during export. Wallet/owner names may be retained in safe messages; they are not automatically extracted from payloads. Logs are diagnostic summaries, not terminal captures or a complete wallet audit trail.

Normal safe workspace closure exports the already sanitized RAM events to the ordinary Agent and deduplicates/orders them with its own events **before** stopping/clearing the protected service. Failure to export or persist these events prevents normal shutdown and retains RAM with an actionable error. Older workers without a diagnostic stream can still be upgraded after the existing idle inspection. Active private operations, required outbox deliveries and pending local cancellation choices still block closure.

The ordinary log can consequently survive reboots. This is an explicitly requested persistence exception for sanitized diagnostics, alongside Services configuration and the sync Denial list. Forced power loss, process crashes and administrator-forced service termination can lose protected events that have not yet been handed over. Saving a log while a workspace is still active includes the ordinary side and previously handed-over events, not that active workspace's RAM stream. Logs can still contain computer/wallet names and operational timing; review them before sharing.
