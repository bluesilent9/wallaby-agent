## Deployment limits and handoff

Dashboard source is not changed. Dashboard V1 Build 9 supports the older Agent Build 7 signed-preview contract. The new authoritative queue, version-2 public previews (vaults/labels/change status) and recovery_required-to-complete relay require [DASHBOARD_BUILD8_UPDATE.md](DASHBOARD_BUILD8_UPDATE.md). Until then new multi-wallet actions are refused for old protocol rows; ordinary services and existing transaction contracts remain available.

Actual two/multi-laptop system SSH, askpass authentication, native GUI/Snap confinement, user-systemd environment/permissions, UFW policy prompts, modem/router reachability and a full mainnet redownload still need deployment checks. The Agent cannot reliably inspect modem firewalls. System SSH remains under the user's control after a transfer.

Recovery preserves the existing pruning mode and target throughout; it never disables pruning or rewrites Core configuration. Wallets, original descriptor timestamps, exact approved labels and vault monitors are registered while network activity is paused, before historical block download resumes. Core records wallet history while pruning old blocks. Completion checks use the wallet’s processed tip and approved public facts rather than trying to rescan deleted blocks afterwards. Ordinary rescans and already-running prepared downloads do not trigger another reindex. No extra automatic wallet/configuration backups are created; an encrypted full-wallet transfer payload is staged only for transport/deferred restoration.

An uncertain wallet operation is never automatically repeated. A service restart leaves private recovery/audit records and may leave Core's existing download running; the user must review a fresh local recovery plan. No production Core instance, user wallet, installed Agent service, Dashboard, SSH listener or firewall was altered during these checks. No independent security audit has been performed.
